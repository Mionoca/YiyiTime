## 五、已知偏差 / 技术债（不阻断当前进度）

| 事项 | 现状 | 计划 |
| --- | --- | --- |
| 「同时只有一个活跃邀请 / 一个进行中申请」靠事务外预检 | 极端并发（同一用户双击）可能产生两条记录；正常操作不会 | M6 前改成事务内原子约束（或给 users 加 pendingInviteCode 字段） |
| 取消邀请后停留在 bind 页的邀请步骤 | 文档 8.2 写的是 navigateBack；当前页内回到「生成邀请」更顺 | 以代码为准，后续如需要再改文档 |
| `requireBound` 的接入 | M2 已挂到 ctx 并由 `couple.updateStartDate` 使用 | M3 起每个双人写接口都必须调用 |
| couples 文档丢失等数据异常时自动重置 coupleId | 已记日志 + 重置，避免白屏 | 依赖真人反馈排查 |
| `hug.respond` 的空/非字符串 `hugId` 返回 `HUG_NOT_FOUND` | 文档 11.4 通用入参规则写的是 `INVALID_INPUT`，但 7.7 端错误表未列该码 | 以端错误表（7.7）为准；客户端不会传空值，后续如补 11.4 再统一 |
| `hug-banner` 不渲染 `outgoing` 状态 | 8.4 组件表列了 `incoming`/`outgoing` 两个属性，但 9.4 / 10.5 只把「TA 需要抱抱」放在横幅，我发出/已回应/已过期用底部按钮 + 心形动画 | 保留 `outgoing` 属性以兼容 8.4 契约，页面不传；若后续想用横幅表达「TA 抱了你」再打开 |
