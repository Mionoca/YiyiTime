## 1. 文档说明

### 1.1 目的

本文档是「小怡怡安」从云开发空模板走向可试用版本的唯一技术依据。读完本文档，开发者应当能够回答：

- 这一版做什么、不做什么、做到什么程度算完成；
- 数据存在哪些集合、字段是什么、谁能读写；
- 云函数如何组织、每个 action 的入参出参和错误码是什么；
- 首页“两个人的小屋”如何用原生 WXML/WXSS 实现；
- 先做哪一步、如何测试、如何发体验版。

### 1.2 读者

- 本项目的前端/云函数开发者（当前主要是项目作者本人）；
- 一周试用后接手迭代的人；
- 需要判断“这个需求该不该现在做”的产品决策者。

### 1.3 范围

本文档覆盖 MVP：

- 情侣绑定；
- 在一起天数与纪念日；
- 场景化首页；
- 心情打卡与抱抱请求；
- 报平安 / 到家了；
- 双人日记（延迟解锁）；
- 愿望清单。

第三层功能、订阅消息提醒、见面基金、应用内解绑、内容安全审核、图片日记列为 P1，本文档只给数据与接口预留，不进入本轮开发。

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 用户 / 本人 | 当前微信用户，以 openid 唯一标识 |
| 伴侣 / TA | 同一 coupleId 下的另一个用户 |
| openid | 微信用户在本小程序下的唯一标识，只能由云函数通过 `cloud.getWXContext()` 获取 |
| coupleId | 情侣关系 ID，格式 `c_` + 16 位十六进制 |
| action | 云函数 `api` 内的业务路由名，如 `home.get` |
| dateKey | 东八区自然日，格式 `YYYY-MM-DD`，如 `2026-11-15` |
| unlockAt | 某条日记对伴侣解锁的服务端时间点（Date） |
| 体验版 | 微信公众平台“版本管理”中设置的体验版本，仅体验成员可打开 |
| P1 | 本轮不做、后续迭代的功能 |
| 订阅消息 | 微信一次性订阅消息，用户每次授权只能发一条，不能当作实时推送 |

### 1.5 约定

- 集合名统一 `snake_case`；字段名、云函数 action、前端变量统一 `camelCase`。
- 所有时间判断以服务端为准。前端不计算“今天”“在一起第几天”“是否解锁”。
- 所有金额（P1 见面基金）以“分”为整数存储，禁止浮点数。
- 文中“必须”表示验收项，“建议”表示可在不阻塞 MVP 的前提下调整。
- 任何接口、集合字段、错误码的变更，必须同步更新本文档第 5、6、7 章与第 14 章验收矩阵。

## 2. 产品范围与验收标准

### 2.1 产品定位

「小怡怡安」不是功能列表，而是**两个人的一间小屋**。用户打开小程序，先看到“我们的房间”，再通过房间里的物件进入功能。所有功能都必须能在场景里找到一个自然入口，这是与市面上大多数情侣小程序的核心差异。

### 2.2 目标用户与场景

- 一对情侣，两个人使用，数据只在这两个人之间共享；
- 可能同城，也可能异地；异地时“报平安”和“抱抱”权重更高；
- 使用频率：每天 1–3 次，每次 1–3 分钟；不做停留时长，做“每天想回来看看”。

### 2.3 产品原则

1. **入口场景化**：首页没有 tabBar、没有九宫格功能列表；台灯=日记，冰箱=愿望，门=报平安，墙历=天数/纪念日，相框=我的，头像气泡=心情。
2. **时间只信服务端**：跨时区、改手机时间都不能让天数、日记解锁、今日打卡出错。
3. **打开时可见，不做实时推送**：抱抱、报平安、日记解锁都靠用户打开小程序时拉取；订阅消息只作为 P1 的补充提醒。
4. **二人共享，服务端鉴权**：任何跨用户数据都必须由云函数校验 coupleId 成员关系；客户端不直接读写数据库。
5. **一周试用优先**：先把两层功能做完整、做稳定，第三层等她用过一周、说出缺什么再决定。

### 2.5 验收标准

#### F1 情侣绑定

- A 在绑定页选择在一起日期，点击“生成邀请码”，得到 6 位数字码，24 小时内有效；
- A 可复制邀请码，也可通过小程序卡片分享；B 打开卡片或手动输入邀请码；
- B 输入后先看到 A 的昵称、头像、在一起日期，必须二次确认才提交申请；
- A 打开小程序能看到“有人想住进来”，确认后双方写入同一 `coupleId`，绑定完成；
- 绑定完成后双方首页都显示对方昵称/头像，且天数使用 A 创建邀请时填写的 `startDate`；
- 同一邀请码只能成功绑定一次；过期、已使用、自己绑自己、任一方已绑定都必须给出明确提示；
- 同一用户同时只能有一个进行中的邀请/申请；连续输错 5 次邀请码，1 小时内禁止再试。

#### F2 在一起天数 + 纪念日

- 首页显示“第 N 天”，N = 东八区日期差 + 1；`startDate` 当天为第 1 天；
- 次日 00:00 后 N 自动 +1，不依赖前端本地日期；
- 显示下一个纪念日（月-日）与剩余天数；当天为纪念日时显示“就是今天”；
- 双方都可以修改 `startDate`，修改后双方看到同一天数；非法日期（未来、格式错误）拒绝；
- 修改手机时间、切换时区，不改变服务端计算结果。

#### F3 场景化首页

- 未绑定：显示空房间、空椅子、邀请入口；不能进入日记/愿望/报平安等双人功能；
- 已绑定：显示双方头像、各自今日心情、今日是否报平安、愿望预览、抱抱入口；
- 点击台灯进日记、冰箱进愿望、门进报平安、墙历进“我们的日子”、相框进“我的”；
- 首页每次 `onShow` 拉取最新数据；从子页返回后状态同步；
- 网络失败显示可重试的错误态，不白屏；无数据时显示空状态而不是空白。

#### F4 心情打卡

- 每天每种心情只能有一条记录；再次选择为更新，不新增；
- 心情四选一：晴/阴/雨/雷；可附不超过 50 字的一句话；
- 首页双方头像旁显示对方今日心情；对方未打卡显示“还没说今天的心情”；
- 跨天后昨日心情不再显示为“今天”，但历史不要求展示（P1 可做心情日历）。

#### F5 抱抱请求

- 点击“我需要抱抱”后生成一条 pending 抱抱，7 天内有效；
- 同一发送者同时只能有一条 pending；重复点击返回已有那条，不重复创建；
- 对方打开首页能看到“TA 需要抱抱”，点击后回应“抱抱 TA”；
- 发送者下次打开能看到“TA 抱了你”；被回应后该条抱抱不再 pending；
- 超过 7 天未回应视为过期，双方都看到“这次抱抱过期了”；
- 不做实时推送；不承诺对方立刻收到。

#### F6 报平安

- 已绑定用户点击“我到家了”，生成一条带服务端时间的记录；
- 10 分钟内重复点击不新增记录，返回“刚刚已经报过平安”；
- 首页显示双方今天是否已报平安；对方未报时显示最近一次时间；
- 时间线按时间倒序，双方记录混排，分页加载；
- 可附不超过 50 字备注（如“加班，晚点回”）。

#### F7 双人日记

- 每天每人可写一句话，长度 1–200 字；当天可修改；
- 当天对方看不到内容，只能看到“TA 已经写了，明天解锁”；自己的内容始终可见；
- 次日 00:00（东八区）后对方内容解锁；解锁由服务端判断，客户端无法绕过；
- 日记列表按日期倒序，分页加载；每条显示双方内容或“未写/未解锁”状态；
- 跨天边界以服务端 `serverNow` 为准；23:59 写的日记，00:00 后对对方可见。

#### F8 愿望清单

- 双方都可以新增、编辑、删除、打勾/取消打勾；
- 标题 1–30 字，备注不超过 100 字；最多 100 条；
- 打勾时有轻量动画；列表显示完成进度；
- 首页桌子显示第一条未完成愿望和完成统计；
- 删除需二次确认；删除后不可恢复。

### 2.6 非目标（本轮明确不做）

- 不做公开社区、匹配、附近的人；
- 不做聊天/即时通讯；
- 不做图片日记、语音、视频；
- 不做真实支付、红包、转账；
- 不做多情侣关系、分手后自动解绑、关系历史；
- 不做订阅消息、定时提醒（P1）；
- 不做内容安全审核（体验版阶段；公开传播前必须补）；
- 不做复杂主题换肤、3D 场景、重力感应。

### 2.7 试用成功标准

一周试用不追求留存数字，重点看：

- 没有崩溃、白屏、数据错乱；
- 对方能独立完成绑定、写日记、报平安、加愿望，不需要开发者每次指导；
- 对方主动提出“我还想要 XX”，且能指出是哪个场景里的缺失；
- 开发者能在 10 分钟内完成一次发版/回滚。

## 3. 技术栈、环境与工程结构

### 3.1 技术选型

| 层 | 选择 | 原因 |
| --- | --- | --- |
| 客户端 | 微信原生小程序（WXML/WXSS/JS） | 用户指定；体积小、云开发集成直接 |
| 后端 | 微信云开发云函数（Node.js） | 免服务器、免鉴权对接、事务与数据库一体 |
| 数据库 | 云开发数据库（文档型） | 与云函数同环境，适合小数据量 |
| 文件存储 | 云开发存储 | 头像上传；按 openid 分目录 |
| 开发语言 | JavaScript（ES2018 语法） | 用户指定；云函数 Node 运行时兼容 |
| 构建 | 无打包步骤 | 原生小程序不需要 Webpack/Vite；减少故障面 |
| 测试 | Node 内置 `node:test`（纯函数） | 零依赖；时间计算必须可单测 |

### 3.8 环境 ID 与仓库卫生

代码要上传 GitHub，环境 ID 的处理原则是：**本地配置、仓库不存、运行时可见、安全不靠它保密**。

#### 3.8.1 先明确：环境 ID 不是密钥

- 云环境 ID 是资源标识，不是授权凭证；知道它不能直接读写数据库；
- 小程序运行时必然携带环境 ID，抓包、解包、内存都能拿到；
- 因此不能把“环境 ID 保密”当作安全边界。真正的边界是：
  - 数据库集合权限“所有用户不可读写”；
  - 云函数 `cloud.getWXContext()` + `requireBound` 鉴权；
  - 邀请码限流、输入校验、日志脱敏；
  - 云开发配额、告警、账单监控。
- 但仍不建议提交：公开仓库会被扫描器收录，增加被盯上的概率，也容易把测试/生产环境暴露给无关的人。

#### 3.8.2 什么能提交、什么不能

| 对象 | 提交 | 说明 |
| --- | --- | --- |
| `miniprogram/config/env.example.js` | 是 | 只有占位符，供复制 |
| `miniprogram/config/env.js` | 否 | 真实环境 ID；`.gitignore` 忽略 |
| `project.config.json` | 是 | 公共项目配置；不写环境 ID |
| `project.private.config.json` | 否 | 本机开发者工具配置；`.gitignore` 忽略 |
| `scripts/check-secrets.js` | 是 | push 前扫描脚本 |
| AppSecret / SecretId / SecretKey | 否 | 任何情况下都不进仓库 |
| 私钥、`.env`、数据库导出 | 否 | 不进仓库、不进日志、不进截图 |

#### 3.8.3 本地配置流程

1. `cp miniprogram/config/env.example.js miniprogram/config/env.js`（Windows 可直接复制文件）；
2. 在 `env.js` 填入云开发控制台 -> 设置 -> 环境 ID；

如果 `project.private.config.json` 在旧提交中已被跟踪，`.gitignore` 不会自动让它失效；执行 `git rm --cached project.private.config.json` 停止跟踪（本地文件保留），再提交。

#### 3.8.4 push 前检查

`check-secrets.js` 会扫描 Git 已跟踪的文件和未被 `.gitignore` 忽略的新文件，可以直接运行：

```bash

```

#### 3.8.5 GitHub 仓库设置

- GitHub 的缓存、fork、PR 引用可能保留旧内容；公开过的密钥一律视为已泄露，必须轮换。

## 4. 总体架构与数据流

### 4.1 架构图

```text
┌──────────────────── 微信小程序（原生 WXML/WXSS/JS）────────────────────┐
│ pages: home / bind / diary / wish / safety / profile                    │
│ components: mood-picker / hug-banner / diary-card / wish-item ...       │
│ utils: api.js（唯一云函数调用入口）/ time.js / constants.js / format.js  │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ wx.cloud.callFunction('api', { action, payload })
                                ▼
┌──────────────────── 云函数 api（Node.js + wx-server-sdk）───────────────┐
│ index.js 路由 → buildContext（openid/user/couple/partner）              │
│ → handler（校验、业务、幂等）→ lib/time.js（东八区/天数/解锁/phase）     │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ 服务端读写
                                ▼
┌──────────────────── 云开发数据库 / 云存储 ──────────────────────────────┐
│ users / couples / bind_invites / moods / hugs / safety_checkins         │
│ diaries / wishes                          avatars/（头像）              │
└──────────────────────────────────────────────────────────────────────────┘
```

外部依赖：

- 微信登录态由云函数 `cloud.getWXContext()` 提供，不需要自建登录；
- 订阅消息、定时触发器属于 P1，本轮不接入；
- 不依赖第三方服务、不依赖自建服务器。

### 4.2 分层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 页面 | 展示、交互、路由、loading/错误态 | 业务规则、时间计算、权限判断 |
| 组件 | 可复用 UI、发事件 | 调云函数、跨组件状态 |
| `utils/api.js` | 统一 `callFunction`、错误归一 | 业务逻辑 |
| 云函数入口 | action 路由、统一响应、requestId | 具体业务 |
| `lib/ctx.js` | openid → user/couple/partner、成员校验 | 业务字段 |
| handler | 参数校验、业务规则、数据库读写、幂等 | 页面展示 |
| `lib/time.js` | 东八区“今天”、天数、解锁、phase、纪念日 | 读取数据库 |
| 数据库 | 持久化、唯一索引、事务 | 展示格式 |

### 4.3 请求生命周期

以 `diary.save` 为例：

1. 页面组装 `{ action: 'diary.save', payload: { content } }`；
2. `wx.cloud.callFunction({ name: 'api', data })`；
3. 云函数入口生成 `requestId`，校验 action 存在；
4. `buildContext`：`cloud.getWXContext().OPENID` → 读 `users` → 读 `couples` → 找 partner；
5. handler 校验 `requireBound`、内容长度；
6. `lib/time.js` 计算 `todayKey`、`unlockAt`；
7. 按 `_id = authorOpenid_date` upsert；
8. 返回 `{ ok: true, data: { diary } }`；
9. 页面收到 `data`，更新 UI；失败则 `{ ok: false, code, message }`，页面 toast 或重试。

统一约定：

- 客户端**不传** openid、coupleId、date、unlockAt；
- 所有时间判断在云函数完成；
- 所有写操作在服务端做幂等或唯一键约束；
- 所有响应带 `requestId`，便于日志排查。

### 4.4 为什么数据访问只走云函数

| 原因 | 说明 |
| --- | --- |
| 身份可信 | openid 只从 `getWXContext` 取，客户端无法伪造 |
| 成员校验 | 每个请求校验 `user.coupleId` 与目标数据 `coupleId` 一致 |
| 时间可信 | 天数、解锁、过期都用服务端时间 + 东八区 |
| 字段保护 | 日记未解锁内容不可能被客户端“绕过 UI”读到 |
| 输入收敛 | 长度、枚举、日期范围统一在服务端校验 |
| 可演进 | 以后换存储、加缓存、加审计，不影响页面 |

代价与取舍：

- 冷启动延迟：单云函数 + 轻依赖，首请求通常可接受；首页失败可重试；
- 调用次数：首页一次聚合，避免页面发 8 个请求；
- 离线：小程序本身不承诺离线写；失败提示重试。

**数据库权限必须设为“所有用户不可读写”**，只允许云函数访问。这不是可选项，否则客户端可直接读日记集合。

### 4.5 实时性边界

微信小程序没有“服务端主动推给在线小程序”的能力。订阅消息需要：

- 用户先点击授权，一次授权通常只能发一条；
- 需要模板、内容审核、用户同意；
- 不能保证到达，也不能作为聊天/状态同步手段。

因此本轮：

- 不做 WebSocket、不做轮询、不做“实时在线”；
- 抱抱、心情、报平安、日记都遵循“**打开时可见**”；
- 刷新时机：`onShow`、子页返回、下拉刷新（子页）、写操作成功后；
- 文案不承诺“实时提醒”，避免用户误解。

### 4.6 单云函数与多函数

选择**单云函数 `api` + action 路由**：

- 共享 `ctx/time/validate/errors`，不重复代码；
- 只部署一个函数，冷启动和日志集中；
- action 显式白名单，未注册 action 直接拒绝；
- 对 2 人使用量足够，不需要微服务拆分。

不采用：

- 每个功能一个云函数：共享代码要靠复制或层，部署繁琐；
- 客户端直读数据库：权限与时间规则无法保证；
- 自建 HTTP 服务：增加域名、证书、运维成本，违背云开发初衷。

### 4.7 环境

| 环境 | 用途 | 数据库 | 云函数 |
| --- | --- | --- | --- |
| dev | 开发联调 | 独立环境 | `api` |
| prod | 体验版/正式 | 独立环境 | `api` |

规则：

- `miniprogram/config/env.js` 只放环境 ID，不放密钥；
- 云函数 `cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })`，跟随部署环境；
- 不在代码里硬编码 `env-xxx`；
- 切换环境只改 `env.js` 并重新编译，不改业务代码；
- 两个环境的集合结构必须一致，靠同一份文档/迁移脚本维护。

## 5. 数据模型

### 5.1 设计原则

- **集合少而清晰**：8 个集合覆盖本轮全部功能；
- **能用 `_id` 表达唯一键就用 `_id`**：减少查询与并发重复；
- **日期与时间戳分开**：业务日期存 `YYYY-MM-DD`（东八区），事件时刻存 `Date`；
- **coupleId 是隔离键**：所有情侣数据必须带 `coupleId`，查询必须带；
- **不信任客户端字段**：openid、coupleId、date、unlockAt 一律服务端生成；
- **软状态、硬数据**：邀请用状态流转不删除；愿望可物理删除；日记不删除；
- **时间戳统一**：`createdAt`/`updatedAt` 用服务端 `db.serverDate()`。

### 5.2 实体关系

```text
users (1) ──── (0..1) couples
  │                    │
  │ creator/applicant  │ 1
  ▼                    ▼
bind_invites (0..*)   moods / hugs / safety_checkins / diaries / wishes (0..*)
```

- 一个用户最多属于一个 couple；
- 一个 couple 固定两个成员；
- 邀请在绑定前存在，绑定后保留为历史记录；
- 所有情侣数据通过 `coupleId` 关联，不通过 openid 猜测。

### 5.3 集合定义

#### 5.3.1 `users`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | 用户 openid |
| `openid` | string | 是 | 与 `_id` 相同，便于返回和日志 |
| `nickname` | string | 是 | 1–12 字，去首尾空格 |
| `avatarFileID` | string | 否 | 云存储 fileID；空串表示默认头像 |
| `coupleId` | string \| null | 是 | 未绑定为 `null` |
| `profileComplete` | boolean | 是 | 昵称非空即 `true` |
| `lastActiveAt` | Date | 否 | 首页访问时节流更新 |
| `bindFailCount` | number | 是 | 连续失败次数，默认 0 |
| `bindFailResetAt` | Date | 否 | 限流窗口起点 |
| `createdAt` | Date | 是 | 首次 `user.get` 创建 |
| `updatedAt` | Date | 是 | 最后更新 |

- 文档 ID 用 openid，天然唯一；
- 不存手机号、位置、性别；
- `nickname` 不做全局唯一。

#### 5.3.2 `couples`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | `c_<16 位 hex>` |
| `memberOpenids` | string[2] | 是 | 两个成员，去重 |
| `startDate` | string | 是 | `YYYY-MM-DD`，东八区 |
| `startDateUpdatedBy` | string | 是 | 最后修改者 openid |
| `status` | string | 是 | 本轮固定 `active` |
| `createdAt` | Date | 是 | 绑定确认时刻 |
| `updatedAt` | Date | 是 | 最后更新 |

- 不存 `daysTogether`，实时计算，避免跨天不准；
- 不存纪念日日期，由 `startDate` 推导；
- 不做解除绑定；P1 如需解绑再加 `status` 流转。

#### 5.3.3 `bind_invites`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | 6 位数字码（000000–999999） |
| `code` | string | 是 | 与 `_id` 相同，便于日志/导出 |
| `creatorOpenid` | string | 是 | 生成者 |
| `applicantOpenid` | string \| null | 否 | 申请者 |
| `status` | string | 是 | `open`/`applied`/`confirmed`/`expired`/`cancelled` |
| `startDate` | string | 是 | 创建时选择 |
| `expiresAt` | Date | 是 | 创建 + 24h |
| `appliedAt` | Date | 否 | 申请时刻 |
| `confirmedAt` | Date | 否 | 确认时刻 |
| `coupleId` | string \| null | 否 | 确认后写入 |
| `createdAt` | Date | 是 | 创建时刻 |
| `updatedAt` | Date | 是 | 最后更新 |

- `_id = code` 保证 6 位码全局唯一；插入冲突时重新生成（最多 5 次）；
- 同一 creator 同时只允许一个 `open`/`applied` 邀请；生成新码时旧码置 `cancelled`；
- 过期不删除，读取时惰性置 `expired`。

#### 5.3.4 `moods`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | `${openid}_${date}` |
| `coupleId` | string | 是 | 归属 |
| `openid` | string | 是 | 作者 |
| `date` | string | 是 | `YYYY-MM-DD`（东八区） |
| `mood` | string | 是 | `sunny`/`cloudy`/`rainy`/`thunder` |
| `note` | string | 否 | ≤50 字 |
| `createdAt` | Date | 是 | 首次打卡 |
| `updatedAt` | Date | 是 | 最后修改 |

- `_id` 保证一人一天一条；重复打卡是更新；
- 日期由服务端 `todayKey` 决定，客户端不能指定。

#### 5.3.5 `hugs`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | `h_<16 位 hex>` |
| `coupleId` | string | 是 | 归属 |
| `fromOpenid` | string | 是 | 发送者 |
| `toOpenid` | string | 是 | 接收者 |
| `status` | string | 是 | `pending`/`hugged`/`expired` |
| `createdAt` | Date | 是 | 发送时刻 |
| `respondedAt` | Date \| null | 否 | 回应时刻 |
| `expiresAt` | Date | 是 | 创建 + 7 天 |

- 同一发送者同时最多一个 `pending`；再点返回原记录；
- 过期在读取时惰性判断，不依赖定时任务；
- 保留历史，不做物理删除。

#### 5.3.6 `safety_checkins`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | 自动 ID |
| `coupleId` | string | 是 | 归属 |
| `openid` | string | 是 | 报平安者 |
| `note` | string | 否 | ≤50 字 |
| `date` | string | 是 | `YYYY-MM-DD`（东八区） |
| `createdAt` | Date | 是 | 报平安时刻 |

- 一天可多条；10 分钟内重复调用返回最近一条并标记 `deduped`；
- 不用 `_id` 唯一键，因为需要保留时间线；
- 时间线按 `createdAt` 倒序。

#### 5.3.7 `diaries`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | `${authorOpenid}_${date}` |
| `coupleId` | string | 是 | 归属 |
| `authorOpenid` | string | 是 | 作者 |
| `date` | string | 是 | `YYYY-MM-DD`（东八区） |
| `content` | string | 是 | 1–200 字 |
| `unlockAt` | Date | 是 | 次日 00:00 +08 |
| `createdAt` | Date | 是 | 创建 |
| `updatedAt` | Date | 是 | 最后修改 |

- `_id` 保证一人一天一条；当天可改，过了 `unlockAt` 拒绝写；
- `unlockAt` 由服务端根据 `date` 计算，不能由客户端传；
- 列表查询按 `coupleId + date`，不能只按作者。

#### 5.3.8 `wishes`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是 | `w_<16 位 hex>` |
| `coupleId` | string | 是 | 归属 |
| `title` | string | 是 | 1–30 字 |
| `note` | string | 否 | ≤100 字 |
| `createdBy` | string | 是 | 创建者 openid |
| `done` | boolean | 是 | 默认 `false` |
| `doneBy` | string \| null | 否 | 完成者 |
| `doneAt` | Date \| null | 否 | 完成时刻 |
| `createdAt` | Date | 是 | 创建 |
| `updatedAt` | Date | 是 | 最后更新 |

- 每对情侣最多 100 条；`wish.add` 前计数；
- 完成/取消完成是幂等 `setDone`，不累加；
- 删除是物理删除；统计随查询实时算。

### 5.4 索引

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `users` | `coupleId` | 按情侣查成员（可选） |
| `couples` | `memberOpenids`（数组索引）、`status` | 按成员查情侣 |
| `bind_invites` | `creatorOpenid + status`、`applicantOpenid + status`、`expiresAt` | 查活跃邀请、清理过期 |
| `moods` | `coupleId + date` | 首页/对方心情 |
| `hugs` | `coupleId + toOpenid + status`、`coupleId + fromOpenid + createdAt` | 待处理/最近发出 |
| `safety_checkins` | `coupleId + date`、`coupleId + createdAt` | 今天是否报平安、时间线 |
| `diaries` | `coupleId + date` | 按天合并 |
| `wishes` | `coupleId + done + createdAt`、`coupleId + createdAt` | 列表排序、计数 |

说明：

- 云开发控制台手工建索引；文档中的索引名仅作建议；
- 控制台没有单独的“数组索引”选项：对数组字段 `memberOpenids` 直接建普通、非唯一的单字段索引即可，云开发底层 MongoDB 会按多键（multikey）索引处理数组元素，`where({ memberOpenids: openid })` 可命中；若控制台明确提示不支持数组字段，再改为按 `coupleId` 反查；
- 所有查询必须带 `coupleId`，避免全表扫描。

### 5.5 状态机

#### 邀请 `bind_invites.status`

```text
open ──apply──▶ applied ──confirm──▶ confirmed
  │                │
  ├──cancel───────▶ cancelled
  └──expire───────▶ expired ◀──expire──┘
```

| 当前 | 事件 | 前置 | 下一状态 | 副作用 |
| --- | --- | --- | --- | --- |
| `open` | `bind.apply` | 非创建者、双方未绑定、未过期 | `applied` | 写 `applicantOpenid`、`appliedAt` |
| `applied` | `bind.confirm` | 创建者、未过期、双方未绑定 | `confirmed` | 事务建 couple、写双方 coupleId、写 `coupleId`/`confirmedAt` |
| `open`/`applied` | `bind.cancel` | 创建者或申请者 | `cancelled` | 无 |
| `open`/`applied` | 到期读取 | `now >= expiresAt` | `expired` | 无 |
| `confirmed` | 任意 | — | 不可变 | 幂等返回 couple |

并发保护：

- `bind.apply` 事务内再次读邀请，状态必须仍为 `open`；
- `bind.confirm` 事务内再次读邀请，状态必须仍为 `applied`，且双方 `coupleId` 仍为空；
- 唯一键 + 事务避免“两人同时确认”或“一人绑两对”。

#### 抱抱 `hugs.status`

```text
pending ──respond──▶ hugged
   └────expire────▶ expired
```

| 当前 | 事件 | 前置 | 下一状态 |
| --- | --- | --- | --- |
| `pending` | `hug.respond` | 当前用户是接收者、未过期 | `hugged` |
| `pending` | 读取 | `now >= expiresAt` | `expired` |

- 过期是惰性判断；首页/接口返回时把过期 `pending` 视为 `expired`；
- 不对历史记录做批量更新，避免定时任务。

### 5.7 数据生命周期

| 数据 | 创建 | 更新 | 删除 | 保留 |
| --- | --- | --- | --- | --- |
| `users` | 首次调用 | 资料/活跃 | 不删 | 长期 |
| `couples` | 绑定确认 | 开始日期 | 不删 | 长期 |
| `bind_invites` | 生成码 | 状态流转 | 不删 | 长期（审计） |
| `moods` | 打卡 | 当天更新 | 不删 | 长期 |
| `hugs` | 发送 | 回应/过期 | 不删 | 长期 |
| `safety_checkins` | 报平安 | 无 | 不删 | 长期 |
| `diaries` | 当天写 | 当天改 | 不删 | 长期 |
| `wishes` | 添加 | 编辑/完成 | 物理删除 | 长期 |

- 本轮不做自动清理；数据量两人使用可忽略；
- 若未来开放图片日记，云存储需单独做孤儿文件清理；
- 头像替换后旧文件不自动删，P1 处理。

### 5.8 一致性规则

1. `users.coupleId` 是成员关系的唯一入口；`couples.memberOpenids` 必须包含该用户；
2. 所有情侣数据写入时 `coupleId` 必须等于 `ctx.user.coupleId`；
3. `diaries`/`moods` 的 `_id` 冲突视为“同一天重复写”，走更新；
4. `bind.confirm` 是唯一跨集合事务；失败则全部回滚；
5. `couple` 文档丢失时，`home.get` 记录错误、重置 `user.coupleId=null`，按未绑定返回；不自动重建；
6. 邀请状态与 `coupleId` 不一致时，以 `couples` 成员关系为准，记录日志并修复邀请状态（P1 定时任务）。

### 6.2 入口与路由

`cloudfunctions/api/index.js`：

```js
const cloud = require('wx-server-sdk');
const handlers = require('./handlers');
const { AppError, toErrorResponse } = require('./lib/errors');
const { buildContext } = require('./lib/ctx');

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });

exports.main = async (event) => {
  const action = event && event.action;
  const rawPayload = event && event.payload;
  const payload = rawPayload && typeof rawPayload === 'object' && !Array.isArray(rawPayload)
    ? rawPayload
    : {};
  const requestId = `${Date.now()}-${Math.random().toString(36).slice(2, 8)}`;

  try {
    if (typeof action !== 'string' || !Object.prototype.hasOwnProperty.call(handlers, action)) {
      throw new AppError('UNKNOWN_ACTION', '这个操作还不存在');
    }

    const { OPENID } = cloud.getWXContext();
    if (!OPENID) {
      throw new AppError('UNAUTHORIZED', '无法识别当前用户');
    }

    const ctx = await buildContext({ openid: OPENID });
    const data = await handlers[action](payload, ctx);
    return { ok: true, data };
  } catch (err) {
    console.error('[api]', JSON.stringify({
      requestId,
      action,
      code: err && err.code,
      message: err && err.message,
    }));
    return toErrorResponse(err, requestId);
  }
};
```

约束：

- `event` 只信任 `action` 与 `payload`；不信任任何客户端传来的 openid、coupleId、角色；
- `payload` 必须是普通对象；数组、字符串、null 一律视为空对象后由校验层报错；
- `handlers` 必须是白名单映射，禁止 `handlers[action]` 直接动态取原型链属性；
- 每个 handler 只返回数据，不返回 `{ok}`；统一由入口包装。

### 6.3 请求上下文

`lib/ctx.js` 负责把 openid 变成可用的业务上下文：

```js
const cloud = require('wx-server-sdk');
const db = cloud.database();

async function buildContext({ openid }) {
  const now = new Date();
  let user = null;

  const userRes = await db.collection('users').doc(openid).get().catch(() => null);
  user = userRes && userRes.data;

  if (!user) {
    user = {
      _id: openid,
      openid,
      nickname: '',
      avatarFileID: '',
      coupleId: null,
      profileComplete: false,
      lastActiveAt: now,
      bindFailCount: 0,
      bindFailResetAt: null,
      createdAt: now,
      updatedAt: now,
    };
    const { _id, ...userData } = user;
    await db.collection('users').doc(openid).set({ data: userData });
  }

  let couple = null;
  let partner = null;

  if (user.coupleId) {
    const coupleRes = await db.collection('couples').doc(user.coupleId).get().catch(() => null);
    couple = coupleRes && coupleRes.data;

    if (couple) {
      const partnerOpenid = (couple.memberOpenids || []).find((id) => id !== openid);
      if (partnerOpenid) {
        const partnerRes = await db.collection('users').doc(partnerOpenid).get().catch(() => null);
        partner = partnerRes && partnerRes.data;
      }
    }
  }

  return { openid, user, couple, partner, db, now };
}

function requireBound(ctx) {
  if (!ctx.user.coupleId || !ctx.couple || ctx.couple.status !== 'active') {
    const { AppError } = require('./errors');
    throw new AppError('NOT_BOUND', '还没有绑定');
  }
  if (!ctx.couple.memberOpenids.includes(ctx.openid)) {
    const { AppError } = require('./errors');
    throw new AppError('FORBIDDEN', '你们还没有绑定');
  }
}

module.exports = { buildContext, requireBound };
```

说明：

- `users` 文档在首次任何请求时自动创建，降低注册步骤；
- 已绑定但 `couples` 文档丢失属于数据异常：`home.get` 会记录日志并把用户重置为未绑定，避免永久白屏；
- `ctx.now` 是本次请求统一时间，handler 内不要再 `new Date()`，保证同一次请求时间一致；
- `requireBound` 只做成员校验，不查 partner；需要 partner 的 handler 自己确认 `ctx.partner` 存在。

### 6.5 参数校验

所有 handler 入口先校验，再查库/写库。`lib/validate.js` 至少提供：

```js
const { AppError } = require('./errors');

function asObject(payload) {
  return payload && typeof payload === 'object' && !Array.isArray(payload) ? payload : {};
}

function string(value, { field, min = 0, max = 200, trim = true, required = false, emptyCode = 'INVALID_INPUT' }) {
  if (value === undefined || value === null) {
    if (required) throw new AppError(emptyCode, `${field}不能为空`);
    return '';
  }
  if (typeof value !== 'string') {
    throw new AppError('INVALID_INPUT', `${field}格式不对`);
  }
  const v = trim ? value.trim() : value;
  if (v.length > max) {
    throw new AppError('TEXT_TOO_LONG', `${field}最多 ${max} 字`);
  }
  if (v.length < min) {
    throw new AppError(emptyCode, `${field}不能为空`);
  }
  return v;
}

function oneOf(value, allowed, field) {
  if (!allowed.includes(value)) {
    throw new AppError('INVALID_INPUT', `${field}不在允许范围内`);
  }
  return value;
}

function boolean(value, field) {
  if (typeof value !== 'boolean') {
    throw new AppError('INVALID_INPUT', `${field}必须是布尔值`);
  }
  return value;
}

function code(value) {
  const v = string(value, { field: '邀请码', min: 6, max: 6, required: true });
  if (!/^\d{6}$/.test(v)) {
    throw new AppError('INVALID_INPUT', '邀请码是 6 位数字');
  }
  return v;
}

module.exports = { asObject, string, oneOf, boolean, code };
```

`lib/time.js` 同时提供日期校验，见 6.7。长度限制：

| 字段 | 最小 | 最大 | 说明 |
| --- | --- | --- | --- |
| 昵称 | 1 | 12 | 去首尾空格后 |
| 心情备注 | 0 | 50 | 可空 |
| 报平安备注 | 0 | 50 | 可空 |
| 日记正文 | 1 | 200 | 去首尾空格后 |
| 愿望标题 | 1 | 30 | 去首尾空格后 |
| 愿望备注 | 0 | 100 | 可空 |
| 邀请码 | 6 | 6 | 仅数字 |
| 分页 limit | 1 | 50 | 一般 1–50、默认 20；日记 1–30、默认 10（见 7.9 / 7.10） |

### 6.6 错误与响应

`lib/errors.js`：

```js
class AppError extends Error {
  constructor(code, message, details) {
    super(message || code);
    this.name = 'AppError';
    this.code = code;
    this.details = details;
  }
}

function toErrorResponse(err, requestId) {
  if (err instanceof AppError) {
    return {
      ok: false,
      code: err.code,
      message: err.message,
      requestId,
    };
  }
  return {
    ok: false,
    code: 'INTERNAL_ERROR',
    message: '服务开小差了，稍后再试',
    requestId,
  };
}

module.exports = { AppError, toErrorResponse };
```

规则：

- 业务错误用 `AppError`，`message` 直接给用户看，必须是中文、可行动；
- 未知异常一律 `INTERNAL_ERROR`，不把堆栈、SQL/集合名、SDK 错误返回给客户端；
- 日志只记录 `requestId`、`action`、`code`、`message`、openid 后 6 位；禁止记录正文；
- 客户端只根据 `code` 做分支，`message` 可直接 toast；不要依赖 `message` 文本做逻辑。

完整错误码见第 16 章附录。常见分支：

| code | 场景 | 用户提示 |
| --- | --- | --- |
| `UNAUTHORIZED` | 拿不到 openid | 请重新进入小程序 |
| `INVALID_INPUT` | 参数缺失/类型错 | 填写内容不太对 |
| `PROFILE_REQUIRED` | 未设置昵称就生成邀请码 | 先给自己起个名字吧 |
| `ALREADY_BOUND` | 已绑定还操作绑定 | 你们已经绑定啦 |
| `NOT_BOUND` | 未绑定访问双人功能 | 先邀请 TA 住进来吧 |

| `INVITE_EXPIRED` | 码过期 | 邀请码过期了，让 TA 重新生成 |

### 6.7 时间规则（服务端唯一实现）

`cloudfunctions/api/lib/time.js`：

```js
const TZ_OFFSET_MS = 8 * 60 * 60 * 1000; // 东八区
const DAY_MS = 24 * 60 * 60 * 1000;

const pad2 = (n) => String(n).padStart(2, '0');

/** 任意时刻 → 东八区 YYYY-MM-DD */
function dateKeyOf(input = new Date()) {
  const d = new Date(input.getTime() + TZ_OFFSET_MS);
  return `${d.getUTCFullYear()}-${pad2(d.getUTCMonth() + 1)}-${pad2(d.getUTCDate())}`;
}

/** YYYY-MM-DD 的东八区 00:00 对应的 UTC Date */
function startOfDateKey(dateKey) {
  const [y, m, d] = dateKey.split('-').map(Number);
  return new Date(Date.UTC(y, m - 1, d) - TZ_OFFSET_MS);
}

/** 日期加减，返回 YYYY-MM-DD */
function addDays(dateKey, n) {
  const start = startOfDateKey(dateKey);
  return dateKeyOf(new Date(start.getTime() + n * DAY_MS));
}

/** 在一起第几天；startDate 当天为 1 */
function daysTogether(startDate, todayKey) {
  return Math.floor((startOfDateKey(todayKey) - startOfDateKey(startDate)) / DAY_MS) + 1;
}

/** 某天日记的解锁时刻：次日 00:00 +08 */
function nextUnlockAt(dateKey) {
  return new Date(startOfDateKey(dateKey).getTime() + DAY_MS);
}

/** 首页氛围：morning / day / dusk / night */
function phaseOf(now = new Date()) {
  const d = new Date(now.getTime() + TZ_OFFSET_MS);
  const h = d.getUTCHours();
  if (h >= 6 && h < 9) return 'morning';
  if (h >= 9 && h < 17) return 'day';
  if (h >= 17 && h < 20) return 'dusk';
  return 'night';
}

function daysInMonth(year, month) {
  return new Date(Date.UTC(year, month, 0)).getUTCDate();
}

/** 下一个纪念日；2 月 29 日按当年 2 月最后一天处理 */
function nextAnniversary(startDate, todayKey) {
  const [sy, sm, sd] = startDate.split('-').map(Number);
  const [ty] = todayKey.split('-').map(Number);

  for (let y = ty; y <= ty + 1; y += 1) {
    const day = Math.min(sd, daysInMonth(y, sm));
    const key = `${y}-${pad2(sm)}-${pad2(day)}`;
    if (key === startDate) continue; // 开始那天不算纪念日
    if (key >= todayKey) {
      return {
        date: key,
        daysLeft: Math.round((startOfDateKey(key) - startOfDateKey(todayKey)) / DAY_MS),
        years: y - sy,
      };
    }
  }
  return null;
}

/** 严格校验 YYYY-MM-DD 是真实存在的日期 */
function isValidDateKey(key) {
  if (typeof key !== 'string' || !/^\d{4}-\d{2}-\d{2}$/.test(key)) return false;
  const [y, m, d] = key.split('-').map(Number);
  const dt = new Date(Date.UTC(y, m - 1, d));
  return dt.getUTCFullYear() === y && dt.getUTCMonth() === m - 1 && dt.getUTCDate() === d;
}

/** startDate 允许 2000-01-01 至今天 */
function isValidStartDate(key, todayKey) {
  return isValidDateKey(key) && key >= '2000-01-01' && key <= todayKey;
}

module.exports = {
  TZ_OFFSET_MS,
  DAY_MS,
  dateKeyOf,
  startOfDateKey,
  addDays,
  daysTogether,
  nextUnlockAt,
  phaseOf,
  nextAnniversary,
  isValidDateKey,
  isValidStartDate,
};
```

单元测试必须覆盖：

- `dateKeyOf(new Date('2026-11-15T15:59:59.000Z')) === '2026-11-15'`；
- `dateKeyOf(new Date('2026-11-15T16:00:00.000Z')) === '2026-11-16'`（东八区 00:00）；
- `daysTogether('2024-05-20', '2024-05-20') === 1`；
- `daysTogether('2024-05-20', '2025-05-20') === 366`（2024 闰年，跨 366 天）；
- `nextUnlockAt('2026-11-15').toISOString() === '2026-11-15T16:00:00.000Z'`；
- 2 月 29 日生日/纪念日在平年的处理；
- 跨年、跨月、23:59/00:00 边界；
- `nextAnniversary` 在开始当天、纪念日当天、纪念日次日的结果。

### 6.8 事务：绑定确认

`bind.confirm` 必须在一个事务里完成“建 couple + 两边 user 写 coupleId + 邀请置 confirmed”，否则会出现“一方已绑定、一方没有”的半绑定状态。

```js
const crypto = require('crypto');

async function confirm(payload, ctx) {
  const code = validate.code(payload.code);
  const invite = await ctx.db.collection('bind_invites').doc(code).get().catch(() => null);
  if (!invite || !invite.data) throw new AppError('INVITE_NOT_FOUND', '没有找到这个邀请码');

  const data = invite.data;
  if (data.creatorOpenid !== ctx.openid) throw new AppError('INVITE_NOT_CREATOR', '这个邀请不是你生成的');
  if (data.status === 'confirmed') {
    // 幂等：已确认且本人是成员，直接返回已有关系
    const coupleRes = await ctx.db.collection('couples').doc(data.coupleId).get().catch(() => null);
    const couple = coupleRes && coupleRes.data;
    if (!couple || !couple.memberOpenids.includes(ctx.openid)) {
      throw new AppError('INVITE_USED', '这个邀请码已经用过了');
    }
    const partnerOpenid = couple.memberOpenids.find((id) => id !== ctx.openid);
    const partnerRes = partnerOpenid
      ? await ctx.db.collection('users').doc(partnerOpenid).get().catch(() => null)
      : null;
    const partner = partnerRes && partnerRes.data;
    return {
      coupleId: data.coupleId,
      startDate: couple.startDate,
      daysTogether: time.daysTogether(couple.startDate, time.dateKeyOf(ctx.now)),
      partner: partner ? { nickname: partner.nickname, avatarFileID: partner.avatarFileID } : null,
    };
  }
  if (data.status !== 'applied') throw new AppError('INVITE_NOT_APPLIED', 'TA 还没有申请');
  if (new Date(data.expiresAt).getTime() <= ctx.now.getTime()) {
    throw new AppError('INVITE_EXPIRED', '邀请码过期了，重新生成一个吧');
  }

  const coupleId = `c_${crypto.randomBytes(8).toString('hex')}`;

  const result = await ctx.db.runTransaction(async (transaction) => {
    // 事务内重新读，避免并发
    const inviteNow = (await transaction.collection('bind_invites').doc(code).get()).data;
    if (inviteNow.status !== 'applied') throw new AppError('INVITE_USED', '这个邀请码状态已经变了');
    if (new Date(inviteNow.expiresAt).getTime() <= ctx.now.getTime()) {
      throw new AppError('INVITE_EXPIRED', '邀请码过期了');
    }

    const creator = (await transaction.collection('users').doc(ctx.openid).get()).data;
    const applicant = (await transaction.collection('users').doc(inviteNow.applicantOpenid).get()).data;

    if (creator.coupleId) throw new AppError('ALREADY_BOUND', '你已经绑定了');
    if (applicant.coupleId) throw new AppError('APPLICANT_ALREADY_BOUND', 'TA 已经和别人绑定了');

    const now = ctx.now;
    await transaction.collection('couples').doc(coupleId).set({
      data: {
        memberOpenids: [ctx.openid, inviteNow.applicantOpenid],
        startDate: inviteNow.startDate,
        startDateUpdatedBy: ctx.openid,
        status: 'active',
        createdAt: now,
        updatedAt: now,
      },
    });

    await transaction.collection('users').doc(ctx.openid).update({
      data: { coupleId, updatedAt: now },
    });
    await transaction.collection('users').doc(inviteNow.applicantOpenid).update({
      data: { coupleId, updatedAt: now },
    });
    await transaction.collection('bind_invites').doc(code).update({
      data: { status: 'confirmed', coupleId, confirmedAt: now },
    });

    return { coupleId, applicantOpenid: inviteNow.applicantOpenid, startDate: inviteNow.startDate };
  });

  const applicantRes = await ctx.db.collection('users').doc(result.applicantOpenid).get().catch(() => null);
  const applicant = applicantRes && applicantRes.data;
  return {
    coupleId: result.coupleId,
    startDate: result.startDate,
    daysTogether: time.daysTogether(result.startDate, time.dateKeyOf(ctx.now)),
    partner: applicant ? { nickname: applicant.nickname, avatarFileID: applicant.avatarFileID } : null,
  };
}
```

实现细节：

- `runTransaction` 在部分 SDK 版本不可用；若报错，改用 `startTransaction()` + `commit()`/`rollback()`，逻辑不变；
- 事务内“先读后写”，不要先写再读；
- `coupleId` 在事务外生成，避免事务内随机数冲突；
- 事务失败必须 `rollback`；`runTransaction` 会自动回滚，`startTransaction` 需手动；
- 确认成功后把双方 `bindFailCount` 重置为 0（可在事务内或事务后，失败不影响主流程）；
- 事务返回后如需 partner 资料，再查一次 applicant user，不要在事务内拼多余数据。

### 6.9 绑定失败限流

目的：防止 6 位码被暴力枚举（100 万种，仍应限流）。

- 窗口：1 小时；
- 同一用户连续失败 5 次后，`bind.preview` / `bind.apply` 返回 `BIND_RATE_LIMITED`；
- 失败包括：码不存在、过期、已使用、自己绑自己、被他人抢先；
- 成功 `bind.apply` / `bind.confirm` 后重置 `bindFailCount=0`、`bindFailResetAt=null`；
- 限流状态存 `users`，不用内存（云函数实例不共享）；
- 不在日志里打印完整邀请码。

## 7. API 契约

### 7.1 统一约定

请求：

```js
wx.cloud.callFunction({
  name: 'api',
  data: { action: 'home.get', payload: {} },
});
```

成功：

```json
{ "ok": true, "data": { } }
```

失败：

```json
{
  "ok": false,
  "code": "INVITE_EXPIRED",
  "message": "邀请码过期了，让 TA 重新生成一个",
  "requestId": "1763...-ab12cd"
}
```

约定：

- 云函数始终返回 `ok` 字段，不依赖 HTTP 状态码；
- 所有时间字段返回 ISO 8601 字符串（如 `2026-11-15T15:08:14.000Z`），客户端只做展示格式化；
- 所有 ID 为字符串；`code` 为 6 位数字字符串；
- 未列出的字段客户端应忽略，便于向后兼容；
- 客户端不得把 `message` 当逻辑判断，只按 `code` 分支；
- 分页接口用游标，不用页码；`nextCursor`/`nextBeforeDate` 为 `null` 表示没有更多。

鉴权矩阵：

| action | 登录（有 openid） | 必须已绑定 | 说明 |
| --- | --- | --- | --- |
| `system.ping` | 是 | 否 | 联调 |
| `user.get` / `user.updateProfile` | 是 | 否 | 资料 |
| `bind.*` | 是 | 否 | 绑定过程 |
| `couple.updateStartDate` | 是 | 是 | 修改日期 |
| `home.get` | 是 | 否 | 未绑定返回空屋状态 |
| `mood.*` / `hug.*` / `safety.*` / `diary.*` / `wish.*` | 是 | 是 | 双人功能 |

### 7.4 绑定

#### `bind.create`

- 入参：`{ startDate: 'YYYY-MM-DD', regenerate?: boolean }`；
- 前置：`profileComplete === true`；未绑定；
- 行为：
  - 校验日期 2000-01-01 至今天；
  - 若已有 `open`/`applied` 邀请且 `regenerate !== true`，直接返回现有邀请；
  - `regenerate === true` 时把旧邀请置 `cancelled`，生成新 6 位码；
  - 同一用户同时只有一个活跃邀请；
- 出参：

```json
{
  "code": "482913",
  "startDate": "2024-05-20",
  "expiresAt": "2026-11-16T15:00:00.000Z",
  "state": "code_created"
}
```

- 错误：`PROFILE_REQUIRED`、`ALREADY_BOUND`、`START_DATE_INVALID`。

#### `bind.preview`

- 入参：`{ code: '482913' }`；
- 行为：校验码存在、未过期、状态 `open`、不是自己、双方未绑定；失败计入限流；
- 出参：

```json
{
  "code": "482913",
  "creator": { "nickname": "小怡", "avatarFileID": "cloud://..." },
  "startDate": "2024-05-20",
  "expiresAt": "2026-11-16T15:00:00.000Z",
  "status": "open"
}
```

- 错误：`INVITE_NOT_FOUND`、`INVITE_EXPIRED`、`INVITE_USED`、`INVITE_SELF`、`BIND_RATE_LIMITED`、`ALREADY_BOUND`；
- 说明：不返回 creator 的 openid；预览不占用邀请码。

#### `bind.apply`

- 入参：`{ code }`；
- 行为：再次校验状态，事务内把邀请置 `applied` 并写入 `applicantOpenid`；同一 B 不能同时申请两个码；
- 出参：

```json
{
  "state": "applied_by_me",
  "code": "482913",
  "creator": { "nickname": "小怡", "avatarFileID": "cloud://..." },
  "startDate": "2024-05-20",
  "expiresAt": "2026-11-16T15:00:00.000Z"
}
```

- 错误：同 `bind.preview`，外加 `BIND_ALREADY_APPLIED`。

#### `bind.confirm`

- 入参：`{ code }`；
- 前置：当前用户是 creator；邀请状态 `applied`；未过期；双方未绑定；
- 行为：事务内创建 couple、双方写 `coupleId`、邀请置 `confirmed`；
- 出参：

```json
{
  "coupleId": "c_9f2a1b3c4d5e6f70",
  "startDate": "2024-05-20",
  "daysTogether": 910,
  "partner": { "nickname": "小安", "avatarFileID": "cloud://..." }
}
```

- 错误：`INVITE_NOT_FOUND`、`INVITE_NOT_CREATOR`、`INVITE_NOT_APPLIED`、`INVITE_EXPIRED`、`ALREADY_BOUND`、`APPLICANT_ALREADY_BOUND`；
- 幂等：已 `confirmed` 且本人是成员，返回同一 couple。

#### `bind.cancel`

- 入参：`{ code }`；

```json
      "partnerUnlocked": false,
      "partner": null
```

- 说明：查询必须带 `coupleId`，不能只按 `authorOpenid` 查，否则会漏掉对方。

## 8. 前端设计

### 8.1 应用生命周期与全局数据

- `app.js` 只做云开发初始化，不拉业务数据；避免启动时阻塞。
- `globalData.user`、`globalData.couple` 仅作为跨页展示缓存，不作为可信数据源；页面仍以接口返回为准。
- 首页 `onShow` 拉 `home.get`；子页操作成功后返回首页，首页再次拉取，保证状态同步。
- 不使用全局事件总线；绑定成功用 `wx.reLaunch`，资料修改用 `onShow` 刷新，足够简单。

### 8.3 页面设计

#### 8.3.1 home

`data`：

```js
{
  home: null,          // home.get 的 data
  loading: true,
  error: '',
  showMoodPicker: false,
  showDaysSheet: false,
  showPartnerSheet: false,
  showHugSheet: false,
```

关键逻辑：

```js
Page({
  data: { home: null, loading: true, error: '' },

  onLoad() {
    const info = wx.getWindowInfo();
    this.setData({ statusBarHeight: info.statusBarHeight || 20 });
    this.loadHome();
  },

  onShow() {
    if (this._loaded) this.loadHome({ silent: true });
  },

  async loadHome({ silent = false } = {}) {
    if (!silent) this.setData({ loading: true, error: '' });
    try {
      const home = await api.call('home.get');
      this.setData({ home, loading: false, error: '' });
      this._loaded = true;
    } catch (err) {
      this.setData({ loading: false, error: err.message });
    }
  },
});
```

- `onTapLamp` → `wx.navigateTo({ url: '/pages/diary/index' })`；
- `onTapFridge` / `onTapTableNote` → wish；
- `onTapDoor` → safety；
- `onTapCalendar` → 打开“我们的日子” bottom sheet（天数、纪念日、开始日期、修改入口）；
- `onTapFrame` → profile；
- `onTapMyAvatar` → 打开 mood-picker；
- `onTapPartnerAvatar` → 打开伴侣心情 sheet；
- `onTapHug` → 根据 `hug.outgoing` 状态发送或提示；
- `onRespondHug` → `hug.respond`，成功后刷新；
- `onRetry` → `loadHome()`。

边界：

- `home === null && loading`：显示“正在开门”的骨架，不显示空场景；
- `home.bind.state === 'unbound'`：空椅子 + 邀请按钮；不显示心情/抱抱/日记；
- `home.bind.state === 'applied_by_partner'`：门垫信封 + 红点；点击进 bind 确认；
- `home.couple` 存在但 `partner` 为空：用默认头像 + “TA”，不崩溃；
- 从子页返回时静默刷新，不闪白。

#### 8.3.2 bind

`data`：

```js
{
  mode: 'invite',        // invite | enter
  step: 'profile',       // profile | invite | enter | waiting | confirm
  nickname: '',
  avatarFileID: '',
  startDate: '2026-11-15',
  code: '',
  preview: null,
  status: null,
  loading: false,
  error: '',
}
```

流程：

1. 进入先 `user.get` + `bind.status`；已绑定直接 `reLaunch` 首页；
2. `profileComplete === false`：先显示昵称 + 头像（可选）表单，保存 `user.updateProfile`；
3. 邀请方：日期选择器 → `bind.create` → 显示 6 位码、复制、分享；
4. 输入方：6 位数字输入 → `bind.preview` → 显示对方资料 + 开始日期 + “确认申请”；
5. 申请后进入 `waiting`，显示“等 TA 确认”，提供“刷新状态”和“取消申请”；
6. 邀请方看到申请后进入 `confirm`，显示申请人资料 + “确认绑定”；
7. 绑定成功 `wx.reLaunch({ url: '/pages/home/index' })`；
8. 分享卡片：`onShareAppMessage` 返回 `path: '/pages/bind/index?code=' + code`，标题“来和我一起住进小怡怡安”。

细节：

- 邀请码输入框 `type="number"`、`maxlength="6"`，只保留数字；
- 复制用 `wx.setClipboardData`；
- 日期选择器 `mode="date"`，`end` 为今天（服务端仍会校验）；
- 倒计时只显示“24 小时内有效”，不在前端算精确剩余时间；
- 所有失败用 `wx.showToast({ icon: 'none' })`，并保留当前输入；
- 头像上传：`wx.cloud.uploadFile` 到 `avatars/${Date.now()}-${random}.png`，成功后 `user.updateProfile`；
- 隐私拒绝/上传失败：允许跳过，使用默认头像；昵称必填。

```js
class ApiError extends Error {
  constructor(code, message, requestId) {
    super(message || '服务开小差了');
    this.name = 'ApiError';
    this.code = code || 'INTERNAL_ERROR';
    this.requestId = requestId;
  }
}

function call(action, payload = {}) {
  return wx.cloud.callFunction({
    name: 'api',
    data: { action, payload },
  }).then((res) => {
    const result = res && res.result;
    if (!result) throw new ApiError('EMPTY_RESPONSE', '服务没有返回结果');
    if (result.ok === true) return result.data;
    throw new ApiError(result.code, result.message, result.requestId);
  }).catch((err) => {
    if (err instanceof ApiError) throw err;
    console.error('[api]', action, err);
    throw new ApiError('NETWORK_ERROR', '网络不太好，请稍后再试');
  });
}

function showError(err) {
  wx.showToast({ title: (err && err.message) || '出错了', icon: 'none' });
}

module.exports = { ApiError, call, showError };
```

```js
const TZ = 8 * 60 * 60 * 1000;

function partsOf(iso) {
  const d = new Date(new Date(iso).getTime() + TZ);
  return {
    y: d.getUTCFullYear(),
    m: d.getUTCMonth() + 1,
    d: d.getUTCDate(),
    h: d.getUTCHours(),
    min: d.getUTCMinutes(),
  };
}

const pad2 = (n) => String(n).padStart(2, '0');

function formatTime(iso, todayKey) {
  const p = partsOf(iso);
  const hm = `${pad2(p.h)}:${pad2(p.min)}`;
  const key = `${p.y}-${pad2(p.m)}-${pad2(p.d)}`;
  return key === todayKey ? `今天 ${hm}` : `${pad2(p.m)}-${pad2(p.d)} ${hm}`;
}

function formatDateCN(dateKey) {
  const [, m, d] = dateKey.split('-').map(Number);
  return `${m} 月 ${d} 日`;
}

function formatMonthDay(dateKey) {
  const [, m, d] = dateKey.split('-').map(Number);

}
```

## 9. 场景化首页

### 9.1 概念

首页是一间**两个人的小屋**，不是功能菜单。用户看到的是“我们的生活状态”，功能藏在物件里：

- 台灯 = 日记；
- 冰箱 / 桌上便签 = 愿望；
- 门 = 报平安；
- 墙历 = 在一起天数 / 纪念日；
- 相框 = 我的；
- 头像气泡 = 心情；
- 抱抱按钮 = 抱抱请求。

设计目标：**一眼看到对方今天的状态，第二眼知道该点什么**。不追求 3D、不追求复杂动效，靠布局、光线、文案营造“有人住”的感觉。

### 9.5 心情气泡

- 四个状态：`sunny` 晴、`cloudy` 阴、`rainy` 雨、`thunder` 雷；
- 气泡位置：头像右上方，三角指向头像；不超过屏幕边缘；
- 内容：图标 + 一个字（晴/阴/雨/雷）；备注不显示在场景里，点开对方 sheet 才显示；
- 未打卡：虚线气泡 + “？”；文案“今天心情？”；
- 颜色只做辅助，图标/文字必须可辨；
- 我的气泡可点（打开 mood-picker）；对方气泡只读，点开详情；
- 跨天：服务端返回 `mood=null`，气泡自动回到未打卡。

| 心形上浮 | 发送/收到抱抱 | 绝对定位心形，`translateY` + `opacity` | 1.4s 一次 |
| 信封脉冲 | 有人申请 | `scale(1→1.04→1)` | 1.8s 循环 |
| 打勾弹跳 | 愿望完成 | `scale(0.9→1.1→1)` | 300ms 一次 |
| 日记解锁微光 | 列表出现已解锁卡片 | `opacity` + 轻微上移 | 400ms 一次 |
| 场景入场 | 首次进入 | 背景淡入 + 家具上移 8rpx | 500ms 一次 |

规则：

- 一次性动画通过添加 class 触发，`setTimeout` 移除；不要永久挂 class；
- 不在 `setData` 高频路径上触发动画；
- 动画失败/不支持时静态也能用；
- 低端机可关闭常驻呼吸动画（P1 提供“减少动效”开关）。

### 9.8 实现分层

| 层 | z-index | 内容 | 是否可点 |
| --- | --- | --- | --- |
| 0 | 0 | 墙、地板、光影 | 否 |
| 1 | 10 | 窗户、墙历、相框 | 墙历/相框可点 |
| 2 | 20 | 沙发、地毯、桌子、台灯、冰箱、门 | 对应物件可点 |
| 3 | 30 | 头像、心情气泡 | 可点 |
| 4 | 40 | 物件文字标签 | 否（跟随父级点击） |
| 5 | 50 | 抱抱横幅、按钮 | 可点 |
| 6 | 60 | 页面级浮层（bottom-sheet 之外） | 视情况 |

WXML 骨架：

```xml
<view class="scene scene--{{home.phase}}" style="padding-top: {{statusBarHeight}}px;">
  <view class="window"></view>
  <view class="calendar" bindtap="onTapCalendar" aria-label="我们的日子">
    <text class="calendar__days">第 {{home.couple.daysTogether}} 天</text>
    <text class="calendar__sub">距纪念日 {{home.couple.anniversary.daysLeft}} 天</text>
  </view>
  <view class="frame" bindtap="onTapFrame" aria-label="我的">
    <image class="frame__avatar" src="{{home.user.avatarFileID || defaultAvatar}}" mode="aspectFill" />
  </view>

  <avatar-bubble user="{{home.user}}" mood="{{home.mood.mine}}" bind:tap="onTapMyAvatar" />
  <avatar-bubble user="{{home.partner}}" mood="{{home.mood.partner}}" bind:tap="onTapPartnerAvatar" />

  <view class="lamp {{home.diary.mineWritten ? 'lamp--on' : ''}}" bindtap="onTapLamp" aria-label="日记"></view>
  <view class="table" bindtap="onTapTableNote" aria-label="愿望">
    <text class="table__note">{{home.wish.previewTitle || '写下下次想做的事'}}</text>
  </view>
  <view class="fridge" bindtap="onTapFridge" aria-label="愿望清单"></view>

</view>
```

实现要点：

- 场景用 `position: relative`，所有物件 `position: absolute`；
- 横向用 `%` 适配宽度，纵向关键位置用 `%`，家具尺寸用 `rpx`；
- 热区最小 88rpx；文字标签加在物件下方，避免遮挡；
- 场景内点击用 `bindtap`，不要用 `catchtap` 阻止所有冒泡；物件的装饰子元素 `pointer-events: none`；
- 自定义导航高度 = `statusBarHeight + 44`；顶部内容避开右上胶囊；
- 底部按钮 `padding-bottom: calc(24rpx + env(safe-area-inset-bottom))`。

### 9.9 适配

- 设计稿基准：750rpx 宽，1624rpx 高（iPhone X 比例）；
- 必测尺寸：320×568、375×667、390×844、430×932；
- 高度不足时：家具整体 `transform: scale(.92)`，或压缩沙发高度；不出现滚动条；
- 宽度不足时：左右物件向内收，文字截断；
- 横屏不支持，`pageOrientation` 保持 `portrait`；
- 刘海屏/灵动岛：顶部用 `statusBarHeight`，底部用 `safe-area-inset-bottom`；
- 大字体模式：标签不设固定高度，允许换行；场景布局不因文字撑破。

### 9.11 资源与升级路径

MVP 用 CSS 手绘：

- 墙、地板、窗户、沙发、桌子、台灯、冰箱、门全部用 `view` + 渐变 + 圆角 + 阴影；
- 头像/心情图标用图片；其余不依赖图片；
- 好处：包体小、可适配、改色快；坏处：精细度有限。

升级路径（不阻塞 MVP）：

1. 先替换窗户/沙发/冰箱/门为手绘 PNG/WebP，保留热区不变；
2. 再整屋替换为 750×1624 背景图，热区用百分比覆盖；
3. 最后才考虑 3D/帧动画，前提是试用后确认场景是留存关键。

约束：

- 不使用来源不明的网图；自制或购买授权；
- 背景图 < 300KB，避免首屏慢；
- 替换资源时热区坐标必须重新校对四档机型。

### 9.12 空态与错误态

- 未绑定：空椅子 + 一盏暗灯 + “屋里还缺一个人”；按钮“邀请 TA 住进来”；
- 已生成邀请：门垫信封 + “等 TA 输入邀请码”；可查看/复制；
- 有人申请：信封脉冲 + “有人在等你”；按钮“去看看”；
- 加载失败：保留上次场景，底部浮层“小屋的门卡住了”+“再试一次”；
- 首次加载失败：显示简化房间轮廓 + 重试，不白屏；
- 对方资料缺失：默认头像 + “TA”，不显示错误。

## 10. 核心流程时序

### 10.1 首次进入

```text
用户           小程序                    云函数 api                  数据库
 │  打开           │                          │                         │
 │───────────────▶│ app.onLaunch             │                         │
 │                │ cloud.init(env)           │                         │
 │                │ home.onLoad               │                         │
 │                │──────── home.get ────────▶│ buildContext            │
 │                │                          │──── users.doc(openid) ─▶│ 不存在
 │                │                          │◀─── null ───────────────│
 │                │                          │──── users.set(new) ────▶│ 创建
 │                │                          │◀─── user ───────────────│
 │                │◀── { user, bind:unbound }│                         │
 │  看到空屋       │ profileComplete=false    │                         │
 │  点“先起个名字” │──── navigateTo bind ────▶│                         │
```

要点：

- 首次请求自动建 `users` 文档，不单独做注册页；
- `profileComplete=false` 时首页显示“先给自己起个名字”，点击进 bind 的资料步骤；
- 资料未完成不阻塞浏览空屋，但不能生成邀请码；
- 昵称、头像保存后 `profileComplete=true`，回到邀请/输入码界面。

### 10.2 绑定

```text
A（邀请方）        小程序 A              云函数 api               数据库
 │ 选开始日期         │                       │                       │
 │──────────────────▶│ bind.create           │                       │
 │                   │──────────────────────▶│ 校验资料/未绑定       │
 │                   │                       │── 生成 6 位码 ───────▶│ bind_invites.set
 │                   │◀── { code, expiresAt }│                       │
 │ 分享/口述 code     │                       │                       │

B（输入方）        小程序 B              云函数 api               数据库
 │ 输入 code          │                       │                       │
 │──────────────────▶│ bind.preview          │                       │
 │                   │──────────────────────▶│ 校验码/非自己/未过期  │
 │                   │◀── { creator, startDate }                     │
 │ 确认申请           │                       │                       │
 │──────────────────▶│ bind.apply            │                       │
 │                   │──────────────────────▶│ 事务：open→applied    │
 │                   │                       │── applicantOpenid ───▶│
 │                   │◀── { state: applied_by_me }                   │

A                 小程序 A              云函数 api               数据库
 │ 看到“有人在等你”   │                       │                       │
 │ 确认绑定           │ bind.confirm          │                       │
 │──────────────────▶│──────────────────────▶│ 事务：                │
 │                   │                       │ 1. 校验 applied       │
 │                   │                       │ 2. 双方 coupleId 为空 │
 │                   │                       │ 3. 建 couples         │
 │                   │                       │ 4. 双方 users.coupleId│
 │                   │                       │ 5. 邀请 confirmed     │
 │                   │◀── { coupleId, ... }  │                       │
 │ reLaunch 首页      │                       │                       │
```

关键约束：

- 预览不占用码，只有 `apply` 才进入 `applied`；
- 确认只能由创建者发起；申请者不能自己确认；
- 确认是事务，任何一步失败全部回滚；
- 已确认后重复确认，若本人是成员则幂等返回同一 couple；
- 双方都已绑定时，任何绑定写操作返回 `ALREADY_BOUND` / `APPLICANT_ALREADY_BOUND`。

### 10.3 首页加载

```text
home.onShow
  → api.call('home.get')
  → buildContext（openid/user/couple/partner）
  → 未绑定：读自己的活跃邀请 → bind.state
  → 已绑定：
      1. 读 couple（缺失则重置并返回未绑定）
      2. 读今日 moods（两人）
      3. 读 incoming pending hug（to=me）
      4. 读 outgoing 最近 hug（from=me）
      5. 读今日 safety（两人）+ 对方最近一条
      6. 读今日 diaries（两人）
      7. 读 wishes 统计 + 第一条未完成
      8. 计算 daysTogether / anniversary / phase
  → 返回聚合 JSON
  → 页面 setData，渲染场景
```

失败处理：

- 核心 `user/couple` 失败：整页错误 + 重试；
- 可选区块（mood/hug/safety/diary/wish）单块失败：记日志，该块返回 `null`，其余正常；
- 首页静默刷新失败：保留旧数据，toast 不打断；
- 从子页返回：`onShow` 静默刷新，避免白屏。

### 10.4 心情打卡

```text
点自己头像 → mood-picker 弹出
  → 选晴/阴/雨/雷（可填备注）
  → api.call('mood.set', { mood, note })
  → 服务端 todayKey
  → moods.doc(`${openid}_${todayKey}`).set/update
  → 返回 mood
  → 关闭弹层，更新气泡，播放 200ms 淡入
```

- 同一天重复打卡是更新，不新增；
- 备注 ≤50 字，可空；
- 跨天：首页重新拉取，`mood.mine=null`，气泡回到“？”；
- 对方心情只读；点对方头像看详情，不显示编辑。

### 10.5 抱抱

发送：

```text
点“我需要抱抱”
  → api.call('hug.send')
  → 查自己是否有 pending
      ├─ 有：返回原记录（existing=true）
      └─ 无：创建 hug，to=partner，7 天有效
  → 按钮变“等 TA 抱抱”，心形上浮动画
```

接收：

```text
对方打开首页
  → home.get 返回 hug.incoming（pending 且未过期）
  → 顶部横幅“TA 需要抱抱”
  → 点“抱抱 TA” → hug.respond({ hugId })
  → 服务端校验接收者，pending→hugged
  → 横幅消失，心形动画
```

发送方下次打开：

```text
home.get 返回 hug.outgoing.status = 'hugged'
  → 按钮旁“TA 抱了你”，一次性心形动画
  → 可再次发送（新 hug）
```

边界：

- 7 天未回应：读取时视为 `expired`；发送方可再发；
- 不能抱自己；未绑定不能发；
- 不做实时推送；文案避免“马上提醒 TA”。

### 10.6 报平安

```text
点门 → safety 页
  → 输入备注（可选）→ 点“我到家了”
  → api.call('safety.checkin', { note })
  → 10 分钟内重复：返回最近一条 + deduped=true
  → 否则新增 safety_checkins
  → 刷新时间线；首页门灯变暖
```

时间线：

- `safety.list` 按 `createdAt` 倒序，cursor 分页；
- 双方记录混排，自己的高亮；
- 跨天：`home.get` 用 `todayKey` 判断 `partnerToday`；
- 不在本轮做“超时未打卡提醒”（需订阅消息）。

### 10.7 日记写入与延迟解锁

写入：

```text
点台灯 → diary 页
  → 输入一句话（≤200 字）
  → api.call('diary.save', { content })
  → 服务端 todayKey、unlockAt=次日 00:00+08
  → diaries.doc(`${openid}_${todayKey}`) upsert
  → 今日卡片更新，提示“明天 TA 才能看到”
```

读取：

```text
diary.list({ beforeDate?, limit })
  → 查 coupleId + date < beforeDate，按 date 倒序
  → 每天最多 2 条，合并成一天
  → 对每条：
       mine：始终返回
       partner：now >= unlockAt ? 返回 content : null
  → 返回 partnerWritten / partnerUnlocked
```

边界：

- 当天 23:59 写，次日 00:00 解锁；
- 已解锁的日记不能再改（`DIARY_LOCKED`）；
- 对方没写：`partnerWritten=false`，显示“TA 今天还没写”；
- 对方写了未解锁：只显示锁和“明天 00:00 解锁”，不显示字数、不显示摘要；
- 跨天时页面停留：`onShow` 重新拉第一页；不依赖本地计时器；
- 分页以“天”为单位，不按单条。

### 10.8 愿望

```text
wish 页
  → wish.list：未完成在前（createdAt 升序），完成在后（doneAt 降序）
  → 添加：wish.add → 统计更新
  → 打勾：wish.setDone({ done: true })
        → 写 doneBy/doneAt → 返回 wish+stats → 打勾动画
  → 取消：wish.setDone({ done: false }) → 清空 doneBy/doneAt
  → 编辑：wish.update
  → 删除：wish.remove（二次确认）
```

- 双方都可编辑/完成/删除；
- 完成是显式目标状态，重复点不会累加；
- 上限 100 条，达到后禁用添加；
- 统计实时算，不存冗余计数。

### 10.9 异常路径

| 场景 | 行为 |
| --- | --- |
| 预览后码过期，再申请 | `INVITE_EXPIRED`，提示重新生成 |
| A、B 同时点确认 | 事务串行；后到者读到 `confirmed`，幂等返回 |
| B 在申请后又绑了别人 | `bind.confirm` 检查 `applicant.coupleId`，返回 `APPLICANT_ALREADY_BOUND` |
| 首页时 couple 文档丢失 | 记日志、重置 `user.coupleId`，按未绑定返回 |
| 重复点“我到家了” | 10 分钟内返回最近一条，`deduped=true` |
| 重复点“我需要抱抱” | 返回已有 pending，`existing=true` |
| 日记保存时已过 00:00 | `DIARY_LOCKED`，提示明天再写 |
| 网络超时但服务端已成功 | 客户端提示重试；写操作幂等，重试安全 |
| 用户改手机时间 | 所有判断用服务端时间，无影响 |
| 跨时区 | 业务日期固定东八区，显示按东八区格式化 |

## 11. 安全、隐私与内容安全

### 11.1 数据分级

| 级别 | 数据 | 处理 |
| --- | --- | --- |
| 高敏 | 日记正文、心情备注、报平安备注、愿望备注 | 仅双方可见；日志禁止打印；接口按解锁规则裁剪 |
| 中敏 | openid、coupleId、邀请码、头像 fileID | 不公开；日志脱敏；邀请码只给双方 |
| 低敏 | 昵称、天数、愿望标题 | 双方可见；无公开页 |

本轮没有公开广场、没有陌生人可见内容，攻击面主要是“绕过客户端直接调云函数”。

### 11.2 身份与成员校验

- 唯一身份来源：`cloud.getWXContext().OPENID`；
- 客户端传的 openid/coupleId 一律忽略；
- 每个双人接口先 `buildContext` 再 `requireBound`；
- `requireBound` 校验三件事：`user.coupleId` 非空、`couple.status==='active'`、`couple.memberOpenids` 包含当前 openid；
- 目标数据必须再校验 `data.coupleId === ctx.couple._id`；
- 邀请确认额外校验 `creatorOpenid/applicantOpenid` 角色；
- 抱抱回应校验 `toOpenid === ctx.openid`；
- 任何“按 id 取数据”的接口，先取再校验归属，不直接返回。

### 11.3 数据库与云存储权限

数据库：

- 所有集合权限设为**所有用户不可读写**；
- 只有云函数（管理员权限）可读写；
- 不在客户端 `wx.cloud.database()` 直接查任何业务集合；
- 控制台操作使用管理员账号，不共享。

环境 ID 不是权限边界：它会在客户端可见。数据库安全依赖本节权限、云函数鉴权和限流，而不是环境 ID 保密（详见 3.8）。

云存储：

- `avatars/` 目录：所有用户可读、仅创建者可写（或按云开发最小权限配置）；
- 头像 fileID 会出现在首页/列表，属于双方可见；
- 不允许客户端上传到其他目录；
- 上传前客户端校验图片类型与大小（≤2MB），服务端不信任客户端但仍以 fileID 为引用；
- 不在云存储放日记、备份、导出文件。

### 11.4 输入校验

| 字段 | 规则 | 失败码 |
| --- | --- | --- |
| `nickname` | 去空格，1–12 字 | `INVALID_INPUT` |
| `avatarFileID` | 可空；必须是 `cloud://` 开头 | `INVALID_INPUT` |
| `mood` | 枚举四值 | `INVALID_INPUT` |
| `note`（心情/报平安） | ≤50 字 | `TEXT_TOO_LONG` |
| `content`（日记） | 去空格，1–200 字 | `DIARY_EMPTY` / `TEXT_TOO_LONG` |
| `title`（愿望） | 去空格，1–30 字 | `INVALID_INPUT` / `TEXT_TOO_LONG` |
| `note`（愿望） | ≤100 字 | `TEXT_TOO_LONG` |
| `startDate` | `YYYY-MM-DD`，2000-01-01 至今天 | `START_DATE_INVALID` |
| `code` | 6 位数字 | `INVALID_INPUT` |
| `wishId`/`hugId` | 非空字符串 | `INVALID_INPUT` |
| `limit` | 整数；一般 1–50、日记 1–30（见 7.9 / 7.10） | `INVALID_INPUT` |
| `beforeDate` | `YYYY-MM-DD` | `INVALID_INPUT` |

补充：

- 字符串统一 `trim`；不接受纯空白；
- 不接受富文本/HTML；WXML 默认转义，不用 `rich-text` 渲染用户内容；
- 不接受客户端传 `date`/`unlockAt`/`coupleId`/`openid`；
- 未知字段忽略，不报错，避免版本兼容问题。

### 11.5 邀请码安全

6 位数字只有 100 万种，必须配合约束：

- 24 小时过期；
- 每个用户同时只有一个活跃邀请；
- 同一用户连续失败 5 次，限流 1 小时（`BIND_RATE_LIMITED`）；
- 预览不泄露创建者 openid；
- 不能邀请自己；
- 只有创建者能确认；
- 已确认的码不可复用；
- 日志不打印完整码，只打印后 3 位；
- 不提供“按昵称搜索用户”的接口。

残余风险：知道码的人可在 24 小时内申请。缓解：双方确认 + 预览显示对方资料 + 可取消。产品上要求“线下口述/分享”，不公开贴码。

### 11.6 隐私合规

- 收集：openid（微信提供）、昵称、头像、用户输入内容；
- 不收集：手机号、位置、通讯录、身份证、支付信息；
- 用途：仅用于情侣双方展示与功能实现；
- 存储：微信云开发数据库/云存储，境内；
- 保留：长期，直到用户要求删除；
- 共享：不向第三方共享；
- 头像/昵称使用微信官方 `chooseAvatar`/`nickname` 能力，不调用已受限的 `wx.getUserProfile`；
- 首次使用前展示隐私提示；公众平台配置《用户隐私保护指引》；
- 提供“关于/隐私说明”入口；正式上线前补用户协议；
- 用户要求删除数据：P1 人工处理（云开发控制台删除 users/couples 及相关集合），本轮在“我的”里留联系方式；
- 不面向未成年人单独设计；若发现未成年人使用，按平台规则处理。

### 11.7 内容安全

本轮内容仅双方可见，没有公开传播，但仍需：

- 不做公开广场、不做陌生人匹配、不做评论；
- 昵称、日记、愿望、备注都可能被对方举报；
- MVP 提供“删除自己内容”的能力（日记暂不删，愿望可删；昵称可改）；
- 正式公开发布前，接入微信内容安全 `security.msgSecCheck`（昵称、日记、愿望标题/备注），失败则拒绝或人工复核；
- 提供举报/反馈入口（P1）；
- 不使用 `rich-text` 渲染用户输入，避免 XSS/外链；
- 图片只允许头像，且走微信头像选择器，不允许任意图片上传；
- 若未来做图片日记，必须先做图片安全检测与存储隔离。

### 11.8 日志与脱敏

允许记录：

- `requestId`、`action`、`code`、耗时、`openid` 后 6 位、`coupleId` 后 6 位（6.11 已统一为 6 位，实现按 `slice(-6)`）；
- 邀请码后 3 位；
- 错误堆栈（仅云函数日志，不返回客户端）。

禁止记录：

- 日记正文、心情备注、报平安备注、愿望备注；
- 完整 openid、完整邀请码；
- 头像 fileID 全量；
- 任何密钥、AppSecret、私钥；
- 环境 ID 不作为常规日志字段；排障确需时只记录后 4 位，且不写入客户端响应。

日志保留：使用云开发默认日志；试用期每周导出一次错误摘要；不长期保留正文。

## 12. 可靠性与边界

### 12.1 目标

- 正确性优先：宁可提示失败，不返回错误的天数/解锁内容；
- 两人使用，低并发；不追求 99.99%；
- 数据不丢：云开发数据库为主，试用期每周手动导出；
- 失败可恢复：写操作幂等，读操作可重试；
- 不承诺实时：所有状态“打开时可见”。

### 12.2 失败模式

| 失败 | 表现 | 处理 |
| --- | --- | --- |
| 云函数冷启动 | 首请求 1–3s | 首页 loading；不自动重试写操作 |
| 调用超时 | `callFunction` 失败 | 提示网络问题；读可重试，写先查后重试 |
| 数据库超时/错误 | handler 抛错 | `INTERNAL_ERROR`；日志 requestId；首页重试 |
| 重复提交 | 双击/网络重试 | 唯一键/幂等（见 12.3） |
| 两人同时确认 | 事务冲突 | 后到者读 `confirmed` 幂等返回 |
| 邀请过期 | 读写失败 | 惰性置 `expired`，提示重新生成 |
| couple 文档丢失 | 首页白屏风险 | 重置 `user.coupleId`，按未绑定返回 |
| 手机时间错误 | 天数/解锁错 | 全部服务端时间，客户端不参与 |
| 跨天页面停留 | 心情/日记不更新 | `onShow` 重新拉取；不本地定时 |
| 头像上传失败 | 无头像 | 允许跳过，默认头像 |
| 隐私授权拒绝 | 无法选头像 | 默认头像，昵称仍可填 |
| 云开发配额耗尽 | 全部失败 | 控制台告警；试用期低概率 |

### 12.3 幂等

| action | 幂等键 | 行为 |
| --- | --- | --- |
| `user.updateProfile` | openid | 覆盖写，重复结果一致 |
| `mood.set` | `openid_date` | upsert，重复更新 |
| `hug.send` | 查询自己 pending | 有则返回原记录 |
| `hug.respond` | hugId + 接收者 | 已 `hugged` 返回 `already:true` |
| `safety.checkin` | 10 分钟窗口 | 返回最近一条 + `deduped` |
| `diary.save` | `authorOpenid_date` | upsert；解锁后拒绝 |
| `wish.setDone` | wishId + 目标状态 | 显式设置，重复结果一致 |
| `wish.remove` | wishId | 不存在返回 `removed:false` |
| `bind.confirm` | 邀请 + 成员关系 | 已确认且本人是成员，返回同一 couple |
| `bind.cancel` | 邀请状态 | 已取消/已确认不可再取消 |

### 12.4 限流

- 绑定失败：同一用户 5 次/小时，超限 `BIND_RATE_LIMITED`；
- 绑定成功/窗口过期：重置计数；
- 其他写操作：本轮只做客户端按钮禁用 + 服务端幂等，不做全局限流；
- 若发现异常调用，P1 在网关层加每用户每分钟上限；
- 不对读接口限流，避免误伤正常使用。

### 12.5 时间边界

- 时区固定东八区，不跟随设备；中国无夏令时；
- `todayKey` 以服务端 `ctx.now` 计算；
- 日记 `unlockAt` = 次日 00:00 +08；
- 页面跨天：`onShow` 刷新；不要用 `setInterval` 跨天；
- 首页 `serverNow` 只用于调试/相对时间，不用于业务判断；
- 邀请过期、抱抱过期都用服务端时间；
- 测试用可注入 `now` 的 `time.js`，不 mock 全局 `Date`；
- 设备时间改到未来/过去不影响服务端结果。

### 12.6 并发

- 绑定确认：事务；
- 心情/日记：同一 `_id` 覆盖，最后写入生效；
- 愿望完成：显式 `setDone`，最后写入生效；
- 抱抱发送：查询后插入，极端双设备并发可能产生两条 pending；首页取最近一条，不影响主流程；P1 用事务或唯一键收敛；
- 报平安：允许一天多条，10 分钟去重；
- 邀请生成：`_id` 冲突重试 5 次；同一用户旧邀请先取消；
- 不使用分布式锁。

### 12.7 数据修复

| 问题 | 修复 |
| --- | --- |
| `user.coupleId` 指向不存在的 couple | 控制台把 `coupleId` 置空，`profileComplete` 保留；用户重新绑定 |
| `couple.memberOpenids` 缺一人 | 以 `users.coupleId` 为准人工核对；补成员或重置双方 |
| 邀请 `confirmed` 但 couple 不存在 | 视为脏数据；把邀请置 `cancelled`，双方重置后重新绑定 |
| 邀请 `applied` 但申请人已绑定 | 把邀请置 `cancelled`，通知重新生成 |
| 孤儿头像文件 | P1 脚本按 users.avatarFileID 比对删除 |

原则：修复前先导出受影响集合；只改必要字段；记录操作人和时间。

### 12.8 监控

- 云开发控制台：函数调用次数、错误率、平均耗时、数据库读写、存储用量；
- 日志检索：按 `requestId`、`action`、`code`；
- 试用期每天看一眼错误日志；每周导出一次错误摘要；
- 告警：云开发配额/费用告警；函数错误率连续升高时人工排查；
- 不接入第三方 APM。

### 12.9 降级

- 首页可选区块失败：该块显示空态，其他正常；
- 首页核心失败：整页重试，保留上次缓存（如有）；
- 日记列表失败：保留已加载内容，底部提示“加载失败，点重试”；
- 写失败：不清空用户输入，允许重试；
- 不做离线队列，避免重复写。

### 12.10 容量与配额

- 2 人、8 集合，日增数据 < 100 条；
- 一年数据量 < 10MB，云开发免费额度足够；
- 云函数超时建议 10s、内存 256MB；
- 首页聚合 9–10 次读，控制在 1s 内；
- 图片仅头像，单张 ≤2MB，总存储 < 100MB；
- 若未来开放图片日记，需重新评估存储与流量。

### 14.2 单元测试

`tests/time.test.js`（示例）：

```js
const test = require('node:test');
const assert = require('node:assert');
const {
  dateKeyOf, daysTogether, nextUnlockAt, phaseOf, nextAnniversary,
} = require('../cloudfunctions/api/lib/time');

test('dateKeyOf 东八区跨日', () => {
  assert.equal(dateKeyOf(new Date('2026-11-14T15:59:00Z')), '2026-11-14');
  assert.equal(dateKeyOf(new Date('2026-11-14T16:00:00Z')), '2026-11-15');
});

test('daysTogether 当天为第 1 天', () => {
  assert.equal(daysTogether('2024-05-20', '2024-05-20'), 1);
  assert.equal(daysTogether('2024-05-20', '2024-05-21'), 2);
});

test('nextUnlockAt 次日 00:00 +08', () => {
  assert.equal(
    nextUnlockAt('2026-11-15').toISOString(),
    '2026-11-15T16:00:00.000Z'
  );
});

test('phaseOf 边界', () => {
  assert.equal(phaseOf(new Date('2026-11-14T22:00:00Z')), 'morning'); // 06:00 +08
  assert.equal(phaseOf(new Date('2026-11-15T01:00:00Z')), 'day');     // 09:00 +08
  assert.equal(phaseOf(new Date('2026-11-15T09:00:00Z')), 'dusk');    // 17:00 +08
  assert.equal(phaseOf(new Date('2026-11-15T12:00:00Z')), 'night');   // 20:00 +08
});

test('nextAnniversary 今年未到/已到', () => {
  assert.deepEqual(nextAnniversary('2024-05-20', '2026-11-15'), {
    date: '2027-05-20', daysLeft: 186, years: 3,
  });
  assert.deepEqual(nextAnniversary('2024-05-20', '2026-05-20'), {
    date: '2026-05-20', daysLeft: 0, years: 2,
  });
});
```

补充用例：

- 闰年 2 月 29 日开始日期；
- 12 月 31 日跨年；
- `startDate` 为今天/明天/2000-01-01/1999-12-31；
- `validate` 的空白、超长、非法枚举、非法日期；
- `phaseOf` 四个边界前后 1 分钟。

### 15.3 已定决策

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 数据访问只走云函数 | 身份、成员、时间、解锁内容都能服务端保证 | 冷启动、调用次数 |
| 单云函数 + action 路由 | 共享代码、部署简单、日志集中 | 单点耦合，需 handler 边界 |

| 首页无 tabBar | 场景化是差异点；入口全在物件里 | 新用户学习成本 |

| `wish.setDone` 而非 toggle | 幂等，重复请求不翻转 | 客户端要传目标状态 |

### 15.4 一周试用指标

定量（至少记录）：

- 7 天内打开天数（目标 ≥5 天）；
- 日均打开次数；
- 心情打卡天数/次数；
- 抱抱发送数、回应率；
- 报平安次数；
- 日记写入天数（双方）；
- 愿望新增/完成数；
- 首页/接口错误次数。

定性（访谈问）：

1. 这一周你最先点开的是哪个物件？为什么？
2. 哪个功能你几乎没用？是不知道、不需要，还是不好用？
3. 有没有哪一刻觉得“这个小程序懂我们”？
4. 有没有哪一刻觉得麻烦/幼稚/卡？
5. 如果只能加一个功能，你最想要什么？

成功标准：

- 双方都主动用过至少 3 个功能；
- 7 天内至少 5 天打开；
- 她主动提出至少 1 条改进（说明在乎）；
- 无 P0 数据错误。

失败信号：

- 只打开 1–2 次；
- 只有一方在用；
- 觉得“不如微信直接说”；
- 场景卡顿/点不到。

### 15.5 试用后的决策

不要一次把所有 P1 都做。按以下顺序选一个：

1. 如果抱抱/心情使用高 → 优先做订阅提醒/更明显的情感反馈；
2. 如果日记使用高 → 优先做图片日记/更长的日记；
3. 如果愿望使用高 → 优先做见面基金/愿望回忆；
4. 如果都低 → 先改首页场景和引导，不加功能；
5. 如果她明确说“想要第三层” → 让用户补充第三层，再评审。

### 15.6 假设

- 双方都有微信，且愿意用同一个小程序；
- 使用场景以中文、中国大陆网络为主；
- 只有两个人使用，不公开传播；
- 手机基础库 ≥ 3.18.0，支持 `chooseAvatar`；
- 云开发环境可用，配额足够；
- 用户接受头像/昵称授权；拒绝时可用默认头像；
- 开始日期可修改，双方都接受天数变化；
- 不需要聊天功能（微信本身承担沟通）。
